# 开发历程

> 2026-11-22 立项 → 2026-11-23 收尾。一天内完成需求、两条技术路线迭代、架构三次重构、打包发布。本文记录完整演进与踩坑，作为同类任务的复盘参考。

## 项目来源

实习方出题：制作演示程序，从含参数叠加显示的航拍图/视频中提取文字（航向角、高度、经纬度等），实时输出。

## 决策时间线

### 阶段一：方案定型（doc/需求分析.md、doc/方案选择.md）

- 路线对比：**像素级 OCR（主）** vs 元数据解析（大疆 SRT，作交叉验证加分项）
- 核心设计：ROI 一次标定（OSD 位置固定，面积缩小几十倍 = 速度与抗干扰双赢）、抽帧采样（参数非帧级变化，无需逐帧）、去抖、变化播报

### 阶段二：模型引擎版（v1~v6）

- RapidOCR（PP-OCRv4 模型）+ ROI 标注工具 + 实时 UI
- **坑 1（崩溃）**：工作线程直接写 tkinter 控件 → 非线程安全崩溃。修：消息队列 + 锁，主线程唯一碰界面
- **坑 2（冻结）**：OCR 引擎初始化在主线程加载模型 → 界面冻结被误判崩溃。修：初始化移入工作线程
- **实测不达标**：识别精度低（OSD 小字+大疆专有字体）、速度慢（单 ROI 数百 ms~数 s）→ **决定放弃模型引擎**

### 阶段三：传统模板匹配版（核心转向）

素材约定：**字符恒为白色**（OSD 白字黑边）。流水线：Otsu 二值化 → 连通域切字 → 模板匹配（cv2.matchTemplate 互相关）→ 逻辑修正。

- **坑 3（二值化）**：自适应阈值的 -C 偏移把均匀黑背景切成白色，连通域全错。修：Otsu 全局阈值
- **坑 4（连通域）**：连通域取在反色图上，把"字符间的背景缝"当成了字符。修：字=前景，直接取正图
- **坑 5（细模板作弊）**：撇号等细长模板用朴素 NCC 指标能"冒充"任何方块字。修：cv2.matchTemplate 滑窗互相关 + 宽高比/高度预筛
- **字体查证**：大疆 OSD 字体为专有字体、无公开名称（社区仅 WTFOS root 后可换自制字体）。对策：模板库加 Bahnschrift（微软 DIN 1451 衍生）；**自采集字符模板**（框住素材真实字符+输入真值，像素级匹配 0.9999+，字体未知也能 100% 适配）
- 粘连字符切分：匹配分数低且超宽 → 等宽基准 + 投影谷点微调切分，切后分数提升才采纳

### 阶段四：逻辑分析模块

识别出的是"字符序列"，业务要的是"数值"。规则（全部可配、随模板保存）：

1. 单位分析：字母必在数字之后（前导字母丢弃），`120m`/`1.2km` 全文输出
2. 冒号白名单：只有时间/相机参数类标签保留冒号；时间无冒号自动两位分组
3. 小数分析：整段至多一个点；**间距均匀不补点**（突出间隔 = 1.5×中位间隔）；**白像素校验**（漏检的点必有墨迹）仅数字 ≤2 时启用；识别点可移动到更突出间隔
4. 标签格式语言：`?` = 一位数字，`*` = 不限位数（按原文分隔符位置分割），如 `??:??`、`*:*`（相机参数 7:100）——误读的分隔符被格式字面量吃掉

### 阶段五：架构与性能

- **v7 教训（GIL）**：逐帧识别 + 帧号对应 → 18 个 ROI 的 Python 匹配循环吃满 GIL，读帧线程饿死，播放卡成 PPT。**回滚为间隔采样 + 双线程**
- **v8 向量化**：模板按高度分组预归一化，一次矩阵乘算完一组全部模板 → 单 ROI 190ms → 16ms（**12 倍**）；缓存键改量化网格（容忍视频压缩噪声）
- 变化门控：画面没变的 ROI 只做 absdiff，近零开销
- 暂停收尾：暂停后识别线程把最后一帧处理完，显示值与画面最后对应

### 阶段六：打包发布

- PyInstaller 双 exe（标注 + 实时），目标机器零依赖
- 路径基座（paths.py）：exe 形态下所有数据文件落在 exe 旁边，拷贝即迁移

## 经验总结

1. **GIL 是 Python 多线程的第一约束**：重计算放 numpy/C 层（释放 GIL），或干脆独立进程
2. **先侦察后写码**：二值化参数、框尺寸、字体全部素材相关，拿到素材先试一帧再定方案
3. **逐帧识别的成本要按 ROI 数量估算**：18 框 × 帧级 = 不可行；间隔采样 + 变化门控是正确折中
4. **字体不明时的终极方案**：不要猜字体，从素材自采集字符模板
5. **模型的边界**：通用 OCR 模型在小字/专有字体/实时场景全面败给针对性传统方案——先用数据验证，别默认"上模型"
